MEDISYNC — COMPLETE PROJECT DESCRIPTION / DEVELOPMENT PROMPT
I am developing a college project called MediSync, a Healthcare Coordination & Management System built using ASP.NET Core MVC, .NET 10, Entity Framework Core, SQL Server, and ASP.NET Core Identity.
You are helping me develop this system into a complete, functional, secure, and professional healthcare management web application.
The most important thing is to understand what MediSync is supposed to do as a complete system.
Do not think of MediSync as just a collection of CRUD pages. It should behave like a small centralized healthcare coordination platform where different healthcare users interact with the same patient and healthcare data according to their roles.
1. WHAT IS MEDISYNC?
MediSync stands for a centralized healthcare coordination and management system.
The purpose of the system is to connect different healthcare activities in one application:

Patient
   ↓
Appointment
   ↓
Doctor Consultation
   ↓
Medical Record
   ├── Lab Test
   │      ↓
   │   Laboratory
   │      ↓
   │   Lab Result
   │
   └── Prescription
          ↓
      Pharmacy
          ↓
       Medicine
Instead of storing healthcare information in disconnected places, MediSync keeps the information connected.
The system should allow authorized users to manage the complete patient journey:

Patient Registration
        ↓
Appointment
        ↓
Doctor Consultation
        ↓
Medical Record
        ↓
Lab Tests / Results
        ↓
Prescription
        ↓
Pharmacy / Medicine
        ↓
Patient Medical History
The application should provide different interfaces and permissions depending on whether the logged-in person is an:

Admin
Doctor
Receptionist
Laboratory Staff
Pharmacist
Patient
2. MAIN OBJECTIVE
The main objective of MediSync is:

To provide a centralized role-based healthcare management system that manages patients, doctors, appointments, medical records, laboratory tests, prescriptions, and medicines while ensuring that each type of user can access only the information and operations relevant to their responsibilities.
The application should be:

Easy to understand
Role-based
Secure
Database-driven
Workflow-oriented
Professional-looking
Suitable for a college final project demonstration
3. PROBLEM MEDISYNC SOLVES
A traditional small healthcare environment may have patient information, appointments, prescriptions, laboratory information, and medicine information handled separately.
This creates problems such as:

Patient information duplication
Difficulty tracking appointments
Difficulty maintaining medical history
Poor coordination between doctor and laboratory
Difficulty tracking prescriptions
Difficulty accessing previous records
Unnecessary access to sensitive information
MediSync solves this by maintaining a centralized system.
For example:

Doctor creates lab request
        ↓
Laboratory sees the request
        ↓
Laboratory enters result
        ↓
Doctor sees the result
        ↓
Patient can see the result
Similarly:

Doctor creates prescription
        ↓
Prescription contains medicines
        ↓
Pharmacist views prescription
        ↓
Pharmacist processes medicine

5. USER ROLES
MediSync has six main roles.

1. Admin
2. Doctor
3. Receptionist
4. Laboratory
5. Pharmacist
6. Patient
Each role must have a different responsibility.
A user should not automatically have access to every module.
6. ADMIN
The Admin is the system-level administrator.
The Admin manages the operational and configuration side of MediSync.

Admin responsibilities
The Admin should be able to manage:

Doctors

Receptionists

System data
User/role-related management

7. DOCTOR
The Doctor is responsible for patient consultation and medical care.
The Doctor dashboard should focus on:

Today's appointments
Pending appointments
Completed appointments
Recent patients
Medical records
Pending laboratory tests/results
Prescriptions
Doctor capabilities
The Doctor should be able to:

View relevant appointments
Confirm appointments
Complete appointments
View patient information
View relevant patient history
Create medical records
Enter symptoms
Enter diagnosis
Enter doctor notes
Enter follow-up instructions
Request laboratory tests
View laboratory results
Create prescriptions
Add medicines to prescriptions
A Doctor should not manage system-wide users unless the Admin role gives that ability.
8. RECEPTIONIST
The Receptionist is responsible primarily for front-desk operations.
The Receptionist should be able to:

Register patients
View patient information
Update basic patient information
Create appointments
View appointment schedules
Manage appointment-related information
The Receptionist should not normally have access to private clinical functions such as:

Creating medical diagnoses
Creating medical records
Creating prescriptions
Entering laboratory results
Managing medicine stock
unless a clearly justified requirement exists.
9. LABORATORY STAFF
The Laboratory role is responsible for laboratory requests and results.
The Laboratory dashboard should show:

Tests In Progress
Completed Tests
Recent Results
Laboratory staff should be able to:

Accept/process tests
Update test status
Enter test results
Add report notes
Mark tests as completed
Laboratory users should not create prescriptions or modify medical diagnoses.
10. PHARMACIST
The Pharmacist is responsible for prescriptions and medicine management.
The Pharmacist dashboard should show:

Pending Prescriptions
Processed Prescriptions
Medicine Count
Low Stock Medicines
The Pharmacist should be able to:

View prescriptions
View prescription items
View medicines
Manage medicine information
Update medicine stock
Process prescriptions
The Pharmacist should not create medical diagnoses or laboratory reports.
11. PATIENT
The Patient is the end user of the healthcare system.
The Patient dashboard should focus entirely on the patient's own healthcare information.
The Patient should be able to:

View profile
Update permitted profile information
Book appointment
View own appointments
View appointment status
View own medical records
View own laboratory results
View own prescriptions
View own medical history
A Patient must never be allowed to view another patient's private information.
For example, if a patient tries to manually change:

Patient ID = 10
to:

Patient ID = 11
they must not automatically gain access to Patient 11's records.
Ownership checks are required in addition to hiding navigation links.
12. AUTHENTICATION
MediSync must use ASP.NET Core Identity.
Users should be able to:

Register
Login
Logout
Manage account
The system should support role assignment and role-based authorization.
Authentication determines:

Who is the user?
Authorization determines:

What is this user allowed to do?
Both are required.
13. ROLE-BASED AUTHORIZATION
Authorization should be implemented at the actual controller/action level.
Do not rely only on hiding links.
For example:

[Authorize(Roles = "Admin")]
or:

[Authorize(Roles = "Doctor,Admin")]
where appropriate.
A user should not be able to bypass restrictions by manually entering a URL.
Example:

/Medicines
/MedicalRecords
/Patients
must still enforce permissions even if the navigation link is hidden.

27. IMPORTANT BUSINESS RULES
The system should follow rules such as:

Authentication
Only authenticated users should access protected functionality.

Authorization
Each role gets only its intended functionality.

Patient privacy
Patients can access their own healthcare data, not another patient's data.

Doctor access
Doctors can work with patients and clinical information relevant to their role.

Laboratory access
Laboratory users manage tests/results, not prescriptions.

Pharmacist access
Pharmacists manage medicines/prescriptions, not diagnoses.

Receptionist access
Receptionists handle administrative/front-desk operations, not clinical decision-making.

Admin access
Admins manage system-level operations.
